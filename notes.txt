Campaign Wiki project notes
===========================

Purpose
-------

This is a small, player-driven D&D campaign wiki. It is intended to grow from
player recaps, discoveries, factions, locations, theories, and other campaign
knowledge. Regular articles and recaps are editable by registered users.
Official pages are readable by everyone but can only be created, edited,
restored, or deleted by administrators.

The campaign shop described in early planning remains a separate future
project and is not part of the completed wiki.

Permissions
-----------

- Anonymous visitors can read pages, revisions, categories, search results,
  and referenced images.
- Registration requires an unused one-time invite key.
- Regular users can create and edit articles and recaps and restore their
  non-official revisions.
- Administrators can additionally create/edit official pages, restore official
  snapshots, permanently delete pages or old revisions, and rename/delete
  categories.
- Category deletion removes the live association but preserves its historical
  label inside revision snapshots.

Database schema
---------------

users
- id                  PRIMARY KEY
- username            NOT NULL, UNIQUE
- email               NOT NULL, UNIQUE
- password_hash       NOT NULL
- role                NOT NULL, defaults to "user"; "user" or "admin"
- created_at           NOT NULL, UTC
- session_version      NOT NULL, increments to revoke existing sessions

invite_keys
- id                  PRIMARY KEY
- key_hash            NOT NULL, UNIQUE, SHA-256 of plaintext key
- created_at           NOT NULL, UTC
- used_at              nullable
- used_by              nullable, FK -> users.id

password_reset_tokens
- id                  PRIMARY KEY
- user_id             NOT NULL, FK -> users.id
- token_hash          NOT NULL, UNIQUE, SHA-256 of plaintext token
- created_at           NOT NULL, UTC
- expires_at           NOT NULL, UTC
- used_at              nullable

categories
- id                  PRIMARY KEY
- name                NOT NULL, UNIQUE
- slug                NOT NULL, UNIQUE
- description         nullable
- created_by          NOT NULL, FK -> users.id
- created_at           NOT NULL, UTC

pages
- id                  PRIMARY KEY
- title               NOT NULL, UNIQUE
- slug                NOT NULL, UNIQUE
- page_type           NOT NULL: article, recap, or official
- created_by          NOT NULL, FK -> users.id
- created_at           NOT NULL, UTC
- updated_at           nullable, UTC
- session_number      nullable; required by application for recaps
- current_revision_id nullable, FK -> page_revisions.id

page_revisions
- id                  PRIMARY KEY
- page_id             NOT NULL, FK -> pages.id
- author_id           NOT NULL, FK -> users.id
- body_markdown       NOT NULL
- created_at           NOT NULL, UTC
- edit_summary        nullable
- page_type           NOT NULL; snapshot value
- session_number      nullable; snapshot value
- revision_number     NOT NULL
- UNIQUE (page_id, revision_number)

page_revision_titles
- revision_id         PRIMARY KEY, FK -> page_revisions.id
- title               NOT NULL; snapshot value

page_revision_categories
- id                  PRIMARY KEY
- revision_id         NOT NULL, FK -> page_revisions.id
- category_id         nullable, FK -> categories.id
- category_name       NOT NULL; immutable snapshot label
- UNIQUE (revision_id, category_name)

page_categories
- page_id             NOT NULL, FK -> pages.id
- category_id         NOT NULL, FK -> categories.id
- PRIMARY KEY (page_id, category_id)

page_title_aliases
- id                  PRIMARY KEY
- page_id             nullable, FK -> pages.id
- title               NOT NULL, UNIQUE
- created_at           NOT NULL, UTC

Historical titles stay reserved while their page exists. Permanently deleting
a page removes its aliases so those titles can be reused.

page_update_authors
- page_id             PRIMARY KEY, FK -> pages.id
- user_id             NOT NULL, FK -> users.id

page_links
- id                  PRIMARY KEY
- source_page_id      NOT NULL, FK -> pages.id
- target_page_id      nullable, FK -> pages.id
- target_title        NOT NULL
- UNIQUE (source_page_id, target_title)
- UNIQUE (source_page_id, target_page_id)

page_search (SQLite FTS5 virtual table)
- page_id             unindexed logical reference
- title               current searchable title
- body                current searchable plain-text body

image_assets
- id                  PRIMARY KEY, UUID string
- page_id             nullable, FK -> pages.id
- upload_session      NOT NULL, UUID draft identifier
- uploaded_by         NOT NULL, FK -> users.id
- original_filename   NOT NULL
- width/height         NOT NULL
- master/display/thumbnail byte counts NOT NULL
- created_at           NOT NULL, UTC

revision_images
- revision_id         NOT NULL, FK -> page_revisions.id
- image_id            NOT NULL, FK -> image_assets.id
- PRIMARY KEY (revision_id, image_id)

Image files live below instance/uploads/images. JPEG, PNG, and WebP uploads are
normalized into master (maximum 6000 px), display (maximum 2000 px), and
thumbnail (maximum 320 px) WebP variants. Historical associations keep images
used by old revisions available.

Operations
----------

- The supported production layout is Docker Compose with Caddy in front of a
  single Gunicorn process. See DEPLOYMENT.md for the complete AlmaLinux runbook.
- Production trusts one proxy hop only when `TRUSTED_PROXY_COUNT=1`; never set
  this on a deployment where clients can reach Gunicorn directly.
- Production sets `SESSION_COOKIE_SECURE=true` because Caddy serves it only over
  HTTPS. Leave that unset for plain-HTTP local development.
- `IMAGE_STORAGE_LIMIT_BYTES` controls the application upload quota. Production
  also uses a separate hard-capped filesystem so this is defense in depth.
- Apply schema changes with `flask db upgrade`.
- Generate invites with `python generate_invite.py [--count N]`.
- Generate reset links with `python generate_password_reset.py USERNAME`.
- Change roles with `python manage_user_role.py USERNAME user|admin`.
- Rebuild current search data with `flask rebuild-search-index`.
- Remove abandoned images with `flask cleanup-images --days 30`.
- Inspect image storage with `flask image-storage-report`.
- Back up both the SQLite database and instance/uploads together.

Password resets
---------------

An administrator runs `python generate_password_reset.py USERNAME` and sends
the printed URL privately to that user. The default lifetime is 60 minutes;
`--minutes` accepts 5-1440. `--base-url` or the `WIKI_BASE_URL` environment
variable controls the public origin in the printed link.

Only a SHA-256 token hash is stored. Issuing a new link consumes all earlier
unused links for the account. The reset form uses the same password policy as
registration, returns a generic response for invalid/expired/used links, and
atomically commits the password and token use. A successful reset increments
the user's session version, invalidating all existing login cookies.
